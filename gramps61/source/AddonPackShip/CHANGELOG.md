# Change log (AddonPackShip — Gramps Addon Packaging Tool)
[**QuickStart.md**](QuickStart.md) ● [**README.md**](README.md) ● [**Change Log**](CHANGELOG.md)

## 1.9.19
- **File, folder and command names are no longer translatable.** Names such as `addons-en.json`, `addons-<lang>.json`, `listings/`, `download/`, `MANIFEST`, `.gpr.py`, `APS.ini`, `po/template.pot` and the gettext install commands are used exactly as written by the code and the Addon Manager, so they must stay in English — also in tooltips, where a translated name would send users looking for a file that does not exist. These names are now `{fields}` filled in after translation by a new `fill_names()` helper, so translators see `{listing}` instead of the name (29 strings). A misspelled field in a translation shows as `{field}` and any other formatting problem shows the text unfilled, instead of raising an error. The MANIFEST dialogs now read "MANIFEST is ready for …" instead of inserting the untranslated words "created"/"amended" into a translated sentence.
- **New "Translation:" row with an "Edit translation…" button**, on the Options tab in the Listings frame, under Multilingual. Choose a language (the languages Gramps itself is translated into; the current Gramps language is preselected unless it is English), select addons, and click the button: for each addon, `po/template.pot` is brought up to date, `po/<code>-local.po` is created from it with `msginit` when missing (language and plural rules filled in) or has new strings merged in with `msgmerge` when it exists (existing translations kept, no backup file left), and the file opens in the default `.po` editor. A results window lists each file and the next steps. New engine functions: `prepare_template()` and `prepare_local_po()` in `make_addon.py`.
- **Version tags moved from the bundle header to each addon row.** A bundle has no version; each registration does. A bump now changes only the `version=` of that one `register()` call (found with Python's `ast` module), where it previously changed the first `version=` in every top-level `.gpr.py` of the folder — so for two registrations in one file only the first was bumped, and addons whose `.gpr.py` sits in a sub-folder were not bumped at all. Formatting, comments and quote style are kept. The MANIFEST button stays on the bundle header, since one MANIFEST covers the whole `.addon.tgz`.
- New **Selected** entry in the type filter, just below **All Types**: shows only the plugins that are checked, to review a selection before building. It combines with the search box and the right-click listing filter.
- The search box now sits at the end of the selection row (after the type filter) instead of on a row of its own, giving the addon list one more line.
- **Compile Translations is dimmed when the gettext tools are missing.** When the tool window opens, it checks for `xgettext` and `msgfmt`. When either is missing, the button is dimmed and reads **xgettext missing** (or **msgfmt missing**), with install commands in its tooltip. Previously the button ran anyway: `po/` was created with no `template.pot` in it, and the real "command not found" error went only to the terminal. The README has a new **Translation tools (gettext)** install section.
- **`template.pot` is regenerated at every Compile Translations and every build**, not only when missing, so new strings reach translators without deleting the file by hand. The file is replaced only when its strings, references or header changed; a new `POT-Creation-Date` alone does not count, so an unchanged addon leaves no diff for Git.
- **`template.pot` headers are filled from the `.gpr.py`.** Compile Translations (and every build) now replaces the generic xgettext placeholders: the title becomes "Translation template for the <version> <name> <type> addon for Gramps.", and the copyright holder, year, package name and version, and bug-report address come from the registration. Existing templates are updated in place, so the title follows each version; a hand-written title and the per-translator placeholders are left alone. When a bundle registers several plugins, the first one whose file sits in the top folder of the bundle names the template. Files are rewritten only when something changed.
- **`template.pot` source references are relative.** `xgettext` now runs from inside the addon folder with plain file names, so references read `#: PhotoTaggingGramplet.py:3` instead of the absolute path of the build machine (home folder included). Existing templates have those absolute folder paths removed in place; only the `#:` lines change.
- Compile Translations no longer reports "✓ Created template.pot" when `xgettext` found no translatable strings and wrote no file; it now says so.
- **Compile Translations now says to restart Gramps** whenever it compiled a `.mo` file, in bold red in the results window. Python's `gettext` caches each translation file the first time it is read, so a running Gramps (even after reloading the plugin) keeps showing the old translations. The README has a new **Translating an Addon** section that explains the translator workflow and this restart.

## 1.9.17
- **Fixed stale entries in the Gramps 5.2 listing.** The bundled `make52.py` still has the old upstream single-addon `listing` merge: it inserts the new entry before the first existing line whose `(t, i)` sorts after it, and keeps the addon's old line. AddonPackShip's dedupe then kept the *last* duplicate — the old one — so an addon could be listed at its previous version in `gramps52/listings/addons-en.json` (e.g. Photo Tagging 1.1.3 instead of 1.2.4) while 5.2's `.addon.tgz` and the 6.0/6.1 listings were correct. Success was judged only by `addons-en.json` existing, so nothing reported it. `make60.py`/`make61.py` were not affected.
- New listing check and repair (`_reconcile_listing_with_gpr()` in `make_addon.py`): after every listing run, whichever generator produced it, each `addons-<lang>.json` is compared with what the addon's `.gpr.py` registers now. Missing, stale or duplicated entries for that addon are replaced with the current ones, and a `Repaired addons-en.json: was [...], now [...]` line appears in the results. Files that already match are not rewritten. Extra fields an upstream script adds (e.g. `make61.py`'s `do`) are kept. The bundled `make52.py` is left matching upstream, so **Update Scripts…** never overwrites a local patch.
- When a listing file still contains duplicates of one plugin, the dedupe now keeps the entry with the highest version, not the last one in the file.
- Listing files are now sorted by `n` — the name the Addon Manager shows — case-insensitively, so a listing can be read in the same order as the GUI. They were previously sorted by `z` (package file name). Expect a one-time reordering diff in each `addons-<lang>.json` the next time it is listed.
- **Fixed AddonPackShip changing the language of the whole Gramps session.** `make_addon.py` runs inside Gramps, and while generating each listing language it set Gramps' global `glocale.language` to that language without restoring it. After a Pack and Ship, the session was left on the last language listed (e.g. `uk`). Gramps' Addon Manager uses that same setting to choose which `addons-<lang>.json` to download, so it requested files that do not exist; the resulting 404 warning, logged from the Addon Manager's background thread, could crash Gramps 6.0.8 (a separate thread-safety problem in Gramps' status-bar warning handler). The language is now set only for the moment each listing is generated, and always restored.
- **Smarter Multilingual listings.** With **Multilingual** on, a new `addons-<lang>.json` is now created only when the name or description in the selected addon's `.gpr.py` is actually translated into that language. Previously one was created for every language the addon had any `po/<lang>-local.po` or `.mo` for — even with those strings untranslated — and then filled with English copies of every other addon's entry. Language files that already exist are always updated with the selected addon (translated where possible, English otherwise), so other addons' translations in them stay current. The results dialog says which language files were created, and why any were skipped.
- **New "Remove untranslated listings…" button** (Options tab, Listings frame). For every checked Gramps Version it finds each `addons-<lang>.json` whose names and descriptions all match `addons-en.json` — files that only repeat the English catalog — lists them, and deletes them after confirmation. Files with any translated entry are kept; `po/` and `locale/` are never touched. Kept as an explicit action rather than part of Pack and Ship, to avoid the extra work on every run and a deletion new users would not expect. The comparison is `find_untranslated_listings()` in `make_addon.py`.
- On a first run (no `APS.ini` yet), the tool now opens on the **Options** tab, so new users see the settings that shape every build before starting one.
- **Progress window for long operations.** **Pack and Ship**, **Build Selected**, **Compile Translations**, **Amend Listings** and **Clean** now show Gramps' standard progress window, naming each step (e.g. "Listing PhotoTaggingGramplet for gramps52") with a bar that advances per build and per listing. Previously the window froze until the whole run finished, long enough for the desktop to offer to force-quit Gramps as "not responding".
- The window also keeps redrawing *during* each step: `make_addon.run_command()` accepts a new optional `wait_callback`, and every child process (`msgfmt`, the interpreter check, `make<NN>.py`) is now waited on in short slices that call it. The command-line `make_addon.py` is unchanged.
- The standalone Python interpreter used for upstream `make<NN>.py` listings is now found and checked once per Gramps session, instead of on every listing for every version — roughly halving the number of slow child processes in a multi-version Pack and Ship.

## 1.9.14 (2026-09)

- `check_gpr_version_coverage()` now tells a genuine version-range gate in an addon's `.gpr.py` apart from no gate at all (the common case): a sentinel probe with an implausible version checks whether `register()` fires unconditionally. When it does, every version's coverage now reports as unverified rather than falsely "confirmed compatible" — an addon with no gate never actually claimed compatibility with anything, positive or negative.
- Multi-version builds now show an explicit note when a target version's compatibility was never verified this way, instead of duplicating the package as silently as a confirmed-compatible one.

## 1.9.12 (2026-09)

- `run_upstream_command()`'s interpreter check now actually validates that a candidate Python can import Gramps from the resolved `GRAMPSPATH` (the same imports upstream `make.py`'s own `listing` command needs), instead of only checking that it can run Python at all — catching a version-mismatched system interpreter (e.g. a system `python3` different from the Python version a given Gramps installation's own tree was built for) before wasting a subprocess call on it.
- A version-specific interpreter name (e.g. `python3.13`, parsed from the resolved `GRAMPSPATH`) is now tried ahead of the generic `python3`/`python` on `PATH`, in case a matching interpreter happens to be available.
- When upstream `make.py` reports success (exit 0) but never actually produces a listing — the same silent-failure class the interpreter check above targets — this is now treated as "delegation could not be attempted" and falls back to the bundled English-only listing generator, instead of reporting a hard failure that produces nothing. The real diagnostic is preserved as a note on the fallback's own log entry rather than being lost.

## 1.9.11 (2026-09)

- Removed the 500-character truncation on the session log's failure-detail note for a failed `listing` delegation — a short cap had already once cut off the single most diagnostic detail (the actual resolved `GRAMPSPATH` value) in practice.

## 1.9.10 (2026-09)

- No functional changes. Version number incremented by AddonPackShip's own opt-in per-addon version-bump flag firing during a Pack and Ship run, rather than by a deliberate release.

## 1.9.9 (2026-09)

- Fixed "Pack and Ship" silently discarding build/listing failure details: `show_combined_results()` only ever showed ✓/✗, unlike the standalone Build/Listing buttons, which already showed a truncated error line. It now shows the same detail.
- The session log now includes the actual subprocess output when the upstream `listing` delegation fails, instead of only ever logging the fixed "not a drop-in substitute" explanatory note regardless of the real cause.

## 1.9.7 (2026-09)

- Session log folder icon added next to **📦 Pack and Ship** — opens `logs/` in the OS file browser. Shown only once this session's own log file exists, not merely because logs exist from an earlier day.

## 1.9.6 (2026-09)

- Fixed a crash in `listing`'s upstream delegation when no valid standalone Python interpreter could be found (frozen macOS `.app` / Windows AIO builds) — now caught and treated as "delegation unavailable," falling back to the bundled listing generator instead of taking down the whole Gramps session.
- `_find_real_python_executable()` now validates `sys.executable` directly instead of trusting it whenever `sys.frozen` is unset, since not every frozen packaging sets that flag.
- Removed the redundant `from gramps.gen.const import GRAMPS_LOCALE as glocale; _ = glocale.translation.gettext` from this tool's own `.gpr.py` — `_` is already provided by Gramps' plugin-loader exec namespace (per the `addons-source` project's registration-file convention).
- Added a version-compatibility guard for multi-version builds: before duplicating a built `.addon.tgz` into every checked Gramps Version's folder, checks whether the addon's own `.gpr.py` actually registers under each target version (re-evaluating its own version-range gate, if any) and skips — rather than silently shipping — versions it excludes. An override is available for confirmed-safe exceptions.
