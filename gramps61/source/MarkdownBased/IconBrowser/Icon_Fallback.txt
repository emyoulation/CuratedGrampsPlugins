Found it — and it's a well-documented GTK behavior interacting badly with a small bug in our code, not something obscure. Here's the chain:

1. Icon themes only define fixed-size buckets at conventional even sizes. Every icon theme (Adwaita, hicolor, and almost certainly Gramps' own bundled icon set) ships raster/fixed-size directories at 16, 22, 24, 32, 48px etc. — never odd sizes. Symbolic variants, when not a fully generic scalable SVG, are usually only available at that same narrow set of even sizes too.

2. Our code never passes FORCE_SIZE. Per the GTK docs: "GTK+ will avoid scaling icons that it considers sufficiently close to the requested size... This behaviour can be changed by passing the GTK_ICON_LOOKUP_FORCE_SIZE flag." Without it, an odd-size request just gets whatever bucket GTK considers "close enough" — inconsistently.

3. The real bug — load_symbolic_for_context() silently degrades to full color. Per the official docs: "If the icon is not a symbolic one, the function will return the result from gtk_icon_info_load_icon()" — i.e., plain full color, no error, no signal that a fallback happened.

4. Our code decides whether to call that function using the wrong signal:

The check lookup_name.endswith("-symbolic") tests our own intent (the Python string we built), not what GTK actually resolved. It's true every time we decided to try the symbolic name, regardless of whether GTK's GENERIC_FALLBACK silently substituted the full-color icon underneath because no symbolic asset existed at that exact size. So we always call load_symbolic_for_context() — and per the docs above, that call itself quietly hands back the full-color pixbuf when the resolved icon isn't genuinely symbolic, no error, no signal. Even sizes happen to land on real symbolic buckets and get properly recolored; odd sizes fall through GTK's fallback chain to color and we never notice.

The fix is to ask GTK what it actually resolved, using GtkIconInfo.is_symbolic() — confirmed in the docs above: "Checks if the icon is symbolic or not" — instead of checking our own request string:

Root cause, in short

Two separate bugs compound into the parity pattern you noticed:

1. The dominant one — the local file fallback tier never tried -symbolic filenames at all. Icon themes only define fixed-size directories at conventional even pixel values (16/22/24/32/48/64...). Request an odd size like 17, and the live Gtk.IconTheme cascade in _load_named() typically misses entirely — for both the symbolic and color name, for every candidate — since 17 doesn't land near any real bucket. Execution then falls through to the raster/SVG/IMAGE_DIR local-file search, which was a completely naive name + ".png" lookup with zero symbolic awareness — no -symbolic attempt, ever. So any size that missed the live theme (which even sizes rarely do, and odd sizes almost always do) landed here and got full color unconditionally. I verified this with a fixture reproducing exactly your report: 16/17/24 all now correctly resolve symbolic, and only sizes >32 (by design, regardless of parity) fall back to color.

2. A secondary, smaller bug in the theme-cascade tier itself. The decision to colorize was based on lookup_name.endswith("-symbolic") — a check on the string we built when we decided to try the symbolic name — rather than on what GTK actually resolved. GtkIconInfo.is_symbolic() is the correct, GTK-native way to ask that question; I swapped to it. I also added Gtk.IconLookupFlags.FORCE_SIZE so whichever asset is found gets scaled to the exact requested size consistently, rather than GTK's default "avoid scaling if close enough" behavior producing inconsistent apparent sizes.

Both fixes are in the file above. The local-file fallback fix is the one that actually explains your reported symptom deterministically; the is_symbolic() fix is a correctness improvement for the live-theme path that could otherwise cause similar (if rarer) mismatches independent of size parity.
